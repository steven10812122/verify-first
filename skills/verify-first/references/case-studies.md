# Case studies

Real incidents, generalized from an actual extended agent session, not hypotheticals. Each one is a failure that verification would have caught, plus one case where the discipline was followed and it worked.

## The aislop incident (stage 1: check prior art before committing)

An agent was asked to design a tool that scans AI-generated code for quality problems (duplication, dead code, unsafe patterns) and produces a shareable score. It designed the concept, picked a name, and was about to start implementation — at which point a routine `npm view <name>` check (done almost as an afterthought) turned up an actively maintained competitor with 595 GitHub stars, an organization behind it, commits from hours earlier, and a feature set considerably more complete than the planned MVP.

**What went wrong:** the agent's earlier "has anyone done this?" pass had relied on general web search and training-data recall, which found nothing — because a real, successful, hours-old-commit project can exist without ever having been written about anywhere a web search would surface it. General search and training recall are not a substitute for checking the actual registry where such a project would be listed.

**What verification looked like once applied:** checking the exact candidate name (and close variants) directly against the real package registry and GitHub search, as the *first* step of evaluating any new idea — not a courtesy check after the design was already done.

## The socialify incident (stage 1 and 2: prior art, and re-checking after a pivot)

Later in the same lineage of work, a different tool (a GitHub-repo-to-image generator) was reframed midway through — its selling point was changed from "fun to share" to "fixes a real, common gap: most repos never set a custom social-preview image." That specific reframing was proposed and partly built without a fresh prior-art check, because the *underlying tool concept* had already been checked earlier in the project.

**What went wrong:** the novelty check that had been done covered the original framing, not the new one. When a project's core claim or positioning changes, that is a new claim requiring its own check — an old "we looked and found nothing" does not carry over to a different claim just because it's the same codebase. A follow-up check found a 2,212-star, actively maintained, MLH-Fellowship-backed project that was *already the recommended tool* for exactly that specific positioning, complete with a hosted API and CLI.

**What verification looked like once applied:** treating the pivot itself as a new claim needing a new check, not assuming the earlier clearance still applied.

## The 95% that was actually 30/40 (stage 4: verify against reality, not your own pipeline)

An agent ran a matching engine against real financial filings and reported "95% matched" as a headline result. The number was computed by counting any non-null extraction as a "match" — including cases where the engine had confidently extracted an entire paragraph of unrelated legal boilerplate instead of the intended figure.

**What went wrong:** the metric measured "did the pipeline produce something," not "was the output actually, specifically correct." These are very different questions, and only the second one is what "95% matched" implies to a reader.

**What verification looked like once applied:** manually checking each result against the real, correct value rather than trusting the automated non-null count. The honest number was close to 30 correct out of 40, not 95%. Both the successes and the specific failure pattern (the same phrase appearing many times across a document, with the wrong instance selected) were reported together, not just the corrected headline number in isolation.

## The kebab-case title overflow (stage 5: challenge your own conclusion before presenting it)

A canvas-based title-rendering feature was built, tested against several short project names, and shipped as working. It broke the first time a user tried it on their own real, long, hyphenated project name — the text overflowed off both edges of the canvas, because the wrapping logic only knew how to break on spaces, and the title had none.

**What went wrong:** every internal test case had been a short or naturally-spaced name, because those were the cases that came to mind while building the feature. None of them adversarially stress-tested the feature's actual weak point.

**What verification looked like once applied:** after the bug was found, a regression test was added using the exact real input that broke it, and a systematic pass was made to find other untested extremes (very high numbers, empty lists, zero-length inputs) before those were reported as handled, rather than after a user found each one individually.

## Where the discipline worked: the reweighted evidence pass

Before shipping a set of "why this meeting might not need to happen" rules, each rule's justification (drawn from commonly-repeated claims about meeting size, agendas, and productivity) was checked against real research rather than cited from memory. The check found that the two most commonly *repeated* claims (meeting size and lack-of-agenda effects) had only weak support in a systematic evidence review, while a less-repeated factor (meeting frequency) had the strongest real support. The rules were reweighted to match the actual evidence strength rather than how popular each claim was — the opposite of what shipping from memory would have produced.

## The honest limit of this skill: a same-day quantification attempt found nothing, and that's an honest result, not a failure to hide

After drafting this skill, an attempt was made to measure whether it actually changes behavior: twelve independent, fresh agent runs were split across two scenarios (evaluating a project idea's novelty; reporting a benchmark's accuracy from data engineered to contain three plausible-looking wrong answers), half with this skill's content injected as instructions, half without. The result was a flat null: every condition behaved identically — 6/6 searched before answering the novelty question, and 6/6 reported the true, un-inflated accuracy on the benchmark question, skill or no skill.

**What this does and doesn't mean:** it does not mean the skill has no effect. The real incidents this skill is built from (above) didn't happen in clean, isolated, single-question tests like this one — they happened deep inside a long session, under momentum, after time was already sunk into a direction, with many other things competing for attention. A short isolated test has no sunk cost and no momentum to overcome, so it can't distinguish "the skill helped" from "nothing needed to overcome here in the first place." The honest conclusion is narrower than either "it works" or "it's not needed": in easy, isolated conditions, the model's default behavior was already sufficient, and this test could not speak to the harder condition (long-session momentum) that the skill actually targets, because reproducing that condition in a same-day test is itself an unsolved problem.

This also surfaced a real, documented limit worth stating plainly: Claude Code's own documentation confirms that a loaded skill's content can remain fully present in context while the model simply chooses a different approach under pressure — a natural-language skill is an influence on behavior, not an enforcement mechanism. That's the direct motivation for this plugin also shipping a `Stop` hook (`scripts/check-overclaiming.sh`) that mechanically checks for a narrow set of red-flag claim phrases against whether a search-like tool call happened nearby — a deterministic backstop for the one slice of this problem that's actually mechanically checkable, not a replacement for the broader judgment-based guidance above.

## Stage 1, again: prior art found late, on a differently-phrased re-check

The original novelty check for this skill searched phrasings like "claude skill overclaim," "rigor verification," and "no hallucination citations" and found nothing. Those searches were real, not skipped — but they missed the single most standard industry term for this exact problem: "hallucination" on its own, without "no" in front of it. A later re-check using that plainer phrasing turned up [Telos-evals/anti-hallucination](https://github.com/Telos-evals/anti-hallucination), a real, existing Claude Code skill (1 star, last updated months earlier) that catches four related patterns — fabrication, stale recall, tool-output paraphrase drift, and unhedged confidence — via a silent self-check plus an on-demand `/hallucination-check` audit grading each pattern CLEAN/YELLOW/RED.

**What this does and doesn't mean:** it's real, adjacent prior art, and pretending otherwise would violate the exact principle this skill is named for. It does not fully overlap with this skill: it doesn't address novelty/prior-art checking specifically (the failure mode that actually cost the most in the incidents above), it ships no deterministic hook, and it isn't built from a documented real-incident case base. But its audit mode — grading each response CLEAN/YELLOW/RED against named patterns with transcript quotes — is a genuinely good mechanic this project doesn't have yet and may be worth adopting. Recorded here rather than quietly folded in, because the original novelty search should have used this exact phrasing on the first pass, not a later one prompted by a direct question about it.

## The hook's own two blind spots, found by someone else's bait-test design

A person outside this project's own development proposed four "bait task" tests to check whether the `Stop` hook actually works: a fabricated-citation trap, a novelty-claim trap, a direct trigger of the mechanical hook, and an adversarial-edge-case trap. Checking the hook's actual source against these four (not from memory of what it was supposed to do) surfaced two real gaps, both present since the hook was first written:

1. **The red-flag phrase list was English-only.** A Chinese-language overclaiming statement ("目前沒有人做過完全一樣的" / "這是全新的概念") matched none of the existing patterns and would have passed through unexamined, regardless of whether any verification had actually happened — because the check never looked at the claim in the first place. This is a significant gap for a tool with a non-English-speaking primary user.
2. **A confidently-stated fabricated citation had no shape the hook recognized at all.** The existing red-flag list only matched *certainty phrases* ("100% accurate," "no prior art"); a fabricated citation like "Smith (1998) found that..." contains no such phrase, so it was invisible to the mechanism entirely — arguably the most dangerous gap, since citation fabrication was one of the two motivating failure modes for this whole project.

**What verification looked like once applied:** both gaps were confirmed by running the actual regex against real BSD `grep` with concrete example strings (not assumed from reading the pattern), fixed by adding a Chinese phrase set and a citation-shape pattern (name/year in the standard `Author (Year)` or `(Author, Year)` form, plus a Chinese "in a `<year>` paper/study" construction), each paired with new regression tests proving both the block and the pass-when-evidence-present case. A third proposed test (adversarially stress-testing code before declaring it done) was deliberately *not* turned into a hook rule — a regex has no reliable way to detect "were edge cases actually tried," and a low-precision heuristic there risks blocking on false positives more than it catches real cases. That one stays guidance-only, and this file says so rather than claiming it's solved.

## Fixing the hook introduced three new bugs, found only by deliberately trying to break the fix

Closing the gaps above wasn't the end of it. Each fix was itself adversarially tested afterward -- the same stage-5 discipline this project teaches, applied to its own code -- and that pass found three more real problems, all fixed the same day:

1. **The evidence check could be satisfied by prose that only mentions a tool's name, never actually calling it.** The original evidence check was a bare substring match against the transcript, so an assistant writing "I did a WebSearch just now and confirmed nothing similar exists" would count as verified, even with zero real tool calls anywhere in the session -- the model narrating a search it never ran, defeating the exact mechanism meant to catch unverified claims. Fixed by requiring the literal JSON shape of a real tool invocation (`"name": "WebSearch"` inside a tool_use block) for tool-name evidence, confirmed against a real transcript file's actual JSON structure rather than assumed.
2. **No protection against an infinite block-rewrite-block loop.** The Stop hook input includes a documented `stop_hook_active` field, true exactly when the current Stop event is a re-run caused by a previous Stop hook blocking the turn -- and the script never read it. A claim that genuinely can't be verified in a given environment (no network access, a tool that isn't available) had no way to stop being re-blocked forever. Fixed by exiting clean whenever `stop_hook_active` is true, so the hook only ever blocks once per stop cycle.
3. **The citation-shape pattern flagged ordinary sentences that had nothing to do with citations.** Confirmed by testing it against deliberately unrelated real sentences: "Tesla (2020) delivered record production numbers" and "Our team shipped Project Phoenix (2024) ahead of schedule" both matched the bare `ProperNoun (Year)` shape and would have been blocked as suspected fabricated citations. The Chinese half of the pattern had the same problem from an unbounded `.*`: any message mentioning a year and a research-related word *anywhere*, however unrelated, matched -- confirmed with "公司在2020年成立,後來團隊做的市場研究顯示成長穩定" (a sentence about company founding and market research, not a citation). Fixed by requiring either the parenthetical `(Name, Year)` citation form or an explicit attribution word ("according to", "citing", "per") before the bare form, and by bounding the Chinese pattern's year-to-keyword distance instead of allowing it to span the whole message. Re-tested against both the original false positives (now clear) and the original citation-trap cases (still caught).

**What this run of fixes doesn't and can't close, stated plainly rather than glossed over:** the official Claude Code docs warn that the transcript file backing `transcript_path` "is written asynchronously and may lag the in-memory conversation" -- the exact reason the same docs recommend `last_assistant_message` over parsing the transcript for the final message text. This hook's evidence check has no alternative to reading that same transcript file, since no equivalent "recent tool calls" field exists in the documented Stop hook input. In a live real session, the observed lag was on the order of one to two seconds and the most recent tool call was already present, so this is a small risk in practice, not a demonstrated frequent failure -- but it is a real, doc-confirmed possibility that a tool call made in the last moment before Stop could still be invisible to this check, causing a false block on a claim that actually had just been verified. There is no better data source available in the current hook input to fix this with; it's recorded here as a known limitation of the design, not solved.

## A second adversarial pass found three more, by testing each sub-phrase individually instead of trusting the ones already spot-checked

A follow-up self-review deliberately went sub-pattern by sub-pattern through the Chinese red-flag list, testing each on both its traditional and simplified form individually, rather than trusting that a phrase working in one script variant meant its sibling worked too. Three didn't:

- `沒有人開發過` (traditional) matched, but the fully simplified `没有人开发过` didn't -- the sub-pattern's ending only checked for `過`, never `过`.
- `保證絕對成功` matched, but `保证绝对可行` didn't -- the sub-pattern only had the traditional `保證`, no `保证` alternative anywhere.
- `查無前例` matched, but `查无前例` didn't -- same issue, traditional-only.

Each is now a genuine trad/simplified alternation rather than a partially-covered one. Verified by testing all three previously-missed phrases directly against both BSD and GNU `grep`, plus re-running the full existing test matrix to confirm nothing that used to match stopped matching.

A second, unrelated finding came from actually reading the official Stop-hook documentation's own example JSON rather than skimming past it: it shows `transcript_path` as `"~/.claude/projects/.../thread.jsonl"` -- a leading `~`. A shell variable's contents are never tilde-expanded by `[ -f ... ]` the way a literal `~` in source code is, so if that were ever the literal runtime value rather than just documentation shorthand, the file-exists check would always fail. This script's own fail-open design (a missing transcript file is treated as "can't check, so don't block") means that specific failure mode would have been the *dangerous* direction, not the safe one: every single red-flag-plus-no-evidence case would have silently exited 0 and allowed the claim through, because the file was never found rather than because evidence was actually present -- the mechanical backstop would look like it was working (no crashes, no errors) while never actually blocking anything. It's unverified which of the two the docs actually meant (literal tilde vs. documentation shorthand for a real absolute path), and expanding a leading `~` against `$HOME` before checking costs nothing either way, so the fix went in regardless of which was true -- confirmed with a test that sets `$HOME` to a real temporary directory, passes a literal `~/...` path, and checks that the hook actually reads the resolved file (it blocks on a real, checked, evidence-free file, rather than allowing through a file it never found).
